# BilateralBound

A **масштабируемая** real-time multiplayer игра, построенная по принципам **SOLID** с модульной архитектурой.

## 🚀 Быстрый запуск (Локально)

```bash
# 📦 Установка зависимостей
npm install

# 🚀 Быстрый запуск с браузером
npm run quick-start

# Или по шагам:
npm run dev        # Запуск сервера с автоперезагрузкой
# Затем открыть: http://localhost:3000
```

### 🎮 Как играть:
1. Откройте http://localhost:3000
2. Нажмите **"🚀 Создать новую сессию"**
3. **Превью сразу видно!** 🎯 - управляйте шаром прямо здесь
4. Скопируйте **ссылку для зрителя** (типа /s/abc123)
5. Откройте ссылку зрителя в новом окне
6. Управляйте шаром и следите за ним глазами! 👁️

### 🎯 Новый интерфейс:
- 🎮 **Встроенный контроллер** - управляйте прямо на главной странице
- 👁️ **Мгновенное превью** - шар двигается сразу после создания сессии
- 📱 **Современный дизайн** - красивый градиентный интерфейс
- ⚡ **Быстрое управление** - стрелки, скорость, цвета - всё в одном месте

## 🏗️ Архитектура

Проект полностью реорганизован по принципам SOLID для обеспечения масштабируемости и поддерживаемости. **Новая HTTP-only архитектура снижает нагрузку на сервер и повышает производительность:**

### 🚀 Ключевые изменения (HTTP-only):
- ❌ **Убрана Socket.IO** - больше нет постоянных WebSocket соединений
- ✅ **HTTP API только** - простые REST запросы для управления сессиями
- 🎯 **Клиентская физика** - вся логика движения на фронте
- ⚡ **Низкая нагрузка** - сервер только хранит метаданные сессий

### Серверная архитектура (`src/`)

```
src/
├── config.js          # Централизованная конфигурация
├── logger.js          # Система логирования
├── session-manager.js # Управление жизненным циклом сессий
└── server.js         # Главный HTTP сервер с API
```

### 🌐 HTTP API Endpoints

Сервер предоставляет простое REST API для управления сессиями:

```
POST /api/session                    # Создать сессию
GET  /api/session/new               # Создать сессию (альтернативный метод)
GET  /api/session/:id              # Получить информацию о сессии
POST /api/session/:id/controller/connect    # Контроллер подключился
POST /api/session/:id/controller/disconnect # Контроллер отключился
POST /api/session/:id/viewer/connect       # Зритель подключился
POST /api/session/:id/viewer/disconnect    # Зритель отключился
GET  /health                        # Health check сервера
GET  /api/status                   # Общая статистика сервера
```

### Клиентская архитектура (`public/js/`)

```
public/js/
├── physics.js           # Физика движения (клиентская)
├── client-config.js     # Конфигурация клиента
├── network-manager.js   # HTTP запросы к API
├── game-renderer.js     # Рендеринг игровых объектов
└── input-controller.js  # Обработка пользовательского ввода
```

### 🎮 Клиентская логика движения

- **Физика на клиенте**: Вся логика расчета движения шарика выполняется в браузере
- **Центрирование**: Шарик автоматически центрируется при запуске
- **HTTP polling**: Клиенты периодически опрашивают сервер для получения статуса сессии
- **Самостоятельность**: Каждый клиент работает независимо, снижая нагрузку на сервер

### ⚡ Преимущества HTTP-only архитектуры

- 🚀 **Высокая производительность** - нет постоянных WebSocket соединений
- 📉 **Низкая нагрузка на сервер** - только метаданные сессий
- 🔄 **Простота масштабирования** - стандартные HTTP серверы
- 🛡️ **Надежность** - меньше точек отказа
- ⚡ **Быстрый запуск** - мгновенное подключение клиентов

## 🎯 Принципы SOLID

### 1. Single Responsibility Principle (SRP)
Каждый модуль отвечает только за одну задачу:

- **SessionManager**: только управление сессиями
- **MessageHandler**: только обработка сообщений
- **GameRenderer**: только рендеринг графики
- **NetworkManager**: только сетевое взаимодействие

### 2. Open/Closed Principle (OCP)
Модули открыты для расширения, но закрыты для модификации:

- Физика легко расширяется новыми типами объектов
- Рендерер поддерживает новые визуальные эффекты
- Система событий позволяет добавлять новых слушателей

### 3. Liskov Substitution Principle (LSP)
Все модули взаимозаменяемы через четкие интерфейсы:

- `BallPhysics` имеет единый API для сервера и клиента
- `NetworkManager` абстрагирует сетевые детали
- `GameRenderer` имеет стандартный интерфейс рендеринга

### 4. Interface Segregation Principle (ISP)
Клиенты зависят только от нужных им интерфейсов:

- Controller получает только управляющие методы
- Viewer получает только визуальные данные
- Server использует только необходимые компоненты

### 5. Dependency Inversion Principle (DIP)
Модули высокого уровня не зависят от низкого уровня:

- `BilateralBoundServer` зависит от абстракций, а не конкретных реализаций
- `GameViewer` использует интерфейсы, а не прямые вызовы

## 🌐 Развертывание

Проект настроен для развертывания на Render с файлом `render.yaml`.

### Переменные окружения
- `PORT`: Порт сервера (по умолчанию 3000)
- `LOG_LEVEL`: Уровень логирования (ERROR, WARN, INFO, DEBUG)
- `MAX_SESSIONS`: Максимальное количество сессий
- `MAX_VIEWERS_PER_SESSION`: Максимум зрителей на сессию
