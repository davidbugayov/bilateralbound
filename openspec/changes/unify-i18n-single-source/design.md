# Design: Унификация i18n

## Context

Текущая архитектура загрузки i18n:

```
Статические HTML (index, about, privacy, offer, breathing)
  └── <script src="/js/i18n/i18n.js" defer>
      └── требует IIFE, экспорт в globalThis

SPA (viewer, controller через webpack)
  └── require('./i18n/i18n')
      └── требует CommonJS, module.exports
```

Оба пути используют одинаковую бизнес-логику, но с разной обёрткой. `public/js/i18n/` содержит ручные копии, которые отстают от `src/i18n/`.

## Goals / Non-Goals

**Goals:**
- `src/i18n/` — единственное место правки i18n-логики
- При сборке `public/js/i18n/i18n.js` и `language-selector.js` генерируются автоматически
- Исправить `_notifyReady()` в обеих копиях (querySelectorAll)

**Non-Goals:**
- Не трогаем `lang-preload.js` — он специфичен для статических страниц и не имеет аналога в src
- Не объединяем загрузку статики через webpack
- Не трогаем `csrfFetch` vs `fetch` различие (разный контекст исполнения)

## Decisions

### 1. Механизм кодогенерации: Node.js скрипт при сборке

**Решение**: добавить `scripts/generate-i18n-iife.js`, вызываемый из `npm run build`.

Скрипт читает `src/i18n/` файлы и трансформирует:
- `module.exports = X` → `globalThis.X = X`
- `require(...)` → удалить (уже в globalThis)
- Оборачивает в `(function(root) { ... })(this)`

**Альтернативы рассмотрены**:
- Webpack multi-entry: не подходит, т.к. HTML загружает скрипты как отдельные файлы, а не bundle
- Симлинки: не решают разницу в обёртке и экспортах
- Ручное поддержание двух копий: уже не работает (drift)

### 2. Что генерировать, а что нет

| Файл | Генерировать? | Причина |
|------|--------------|---------|
| `i18n.js` | ✅ Да | Основной модуль с бизнес-логикой |
| `language-selector.js` | ✅ Да | Переключение языков |
| `lang-preload.js` | ❌ Нет | Уникален для статики, нет аналога в src |
| `constants.js` | ❌ Нет | Уже загружается отдельно как `i18n-constants.js` в public |

### 3. Порядок исправления drift'а

Сначала применяем fix `_notifyReady` → `querySelectorAll` в `src/i18n/i18n.js`, затем настраиваем генерацию поверх исправленной версии.

## Risks / Trade-offs

- **Генерация может сломаться при изменении структуры src/i18n/** → Build-шаг падает с явной ошибкой, не маскируя проблему
- **lang-preload.js остаётся ручным** → Риск минимален (66 строк, редко меняется)
- **csrfFetch vs fetch различие** → Оставляем как есть: public/js версия использует `fetch` напрямую т.к. на статических страницах нет CSRF-токена

## Migration Plan

1. Создать `scripts/generate-i18n-iife.js`
2. Исправить `_notifyReady` в `src/i18n/i18n.js`
3. Добавить `generate-i18n-iife` в `npm run build` (перед webpack)
4. Сгенерировать, проверить diff между старыми и новыми public/js/i18n файлами
5. E2E тесты на статических страницах
6. Удалить ручное поддержание public/js/i18n копий из процесса разработки

**Rollback**: восстановить public/js/i18n из git (файлы не удаляются, только перезаписываются при сборке).
